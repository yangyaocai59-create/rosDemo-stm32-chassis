# 0.18.23 同步快照与异常前后冻结记录

日期：2026-10-23。版本 `0.18.23-trace-candidate`。

本版用于查清带载顿挫时发生了什么，尚未烧录、没有实车验收。本次没有打开USB/CH340、发送运动命令或清板上故障。基于未实车验收的0.18.22统一PI候选；不是在板上0.18.21旧补偿路径上仅增加日志，因此将来与0.18.21比较必须注明控制算法也不同。

相对0.18.22，FF/PI、积分上限、PWM上限、输出斜率、安全判据、编码器计数、USB协议及IMU均未调整。驱动只新增诊断请求副本与只读寄存器接口；记录模块不调用运动、使能、清故障或输出写入接口。0.18.22发现的带载前馈/I余量问题仍未解决，不能把诊断版的软件通过说成顿挫修复完成。

## 记录内容与同步边界

仍在motorTask原有的控制处理结束后调用记录函数，不改任务周期。读取runtime、底盘、四轮PI、测速与驱动状态时共用一个外层FreeRTOS临界区，避免普通任务STOP把读取过程分成前后两段。临界区内没有日志、UART等待或控制计算；格式转换在退出临界区后完成。

PC13急停中断优先级为4，仍能打断该临界区。读取前后检查不可自行清除的急停锁存位，发生边界变化会在帧上标记，不能冒充完整的输出提交快照。电气引脚、电机转矩与传感器采样本来就不是同一物理瞬间；新增字段让时间关系可检查，而不是声称实现了示波器级同步。

新增内容：

- `seq`：记录帧序号，**不是USB命令序号，也不是另一个控制循环计数器**。
- `speed_t`、`control_t`：测速源时间与最近输出提交时间；沿用原帧的记录时间`t`及实际测速间隔`dt`。
- 每轮原始归一化增量`dc`与有符号64位累计计数；累计值拆成`total_hi/total_lo`两个无符号32位数输出，解析器恢复原始有符号值。
- 该轮PI目标、原始/滤波反馈、FF/P/I、控制器保存的输出、送入驱动的请求、驱动接受的PWM。
- TIM8可读CCR、ARR、BDTR、CCER，方向GPIO输出位和STBY输出位。
- 控制器`limited`原值及输出边界观察位`obs`。

CCR是CPU读到的预装载寄存器值，**不是引脚波形测量，更不是“驱动力足够”的证明**。`request`是驱动执行方向保护前接受处理的请求；`ctrl`是控制器保存的输出历史，可能已被方向保护的零输出回填，不能将二者混用。

`flags`：1=采样时存在急停锁存，2=读取途中急停锁存变化，4=测速无效/时间不一致/年龄超过40ms，8=ACTIVE时控制器状态或目标/反馈与所读快照不匹配。带非零flags的帧不能用来推导同一控制周期的因果；欠速触发不使用这些帧。

`obs`：1=驱动零输出/换向等待状态，2=积分达到现有50‰限幅，4=FF+P+I幅值超过现有300‰上限，8=驱动请求不同于接受输出。它们是可核实的边界观察值，**不是新加的控制判据或完整的抗积分饱和决策记录**；例如obs=2时PWM仍可能远小于300‰。

## 触发与冻结

固定128帧，通常20ms一帧；单帧248字节，环形缓冲31744字节。不会尝试在RAM中保存任意长完整动作。

1. 首次ACTIVE进入后保留滚动记录。启动前1000ms不触发诊断欠速。
2. 目标幅值至少80cps，且同向原始反馈低于目标25%，或同向滤波反馈低于目标50%，在有效新样本中持续累计100ms，触发第一次欠速记录。重复/无效样本不累计，异常大间隔不能替代持续欠速证据。
3. 触发后再保存25帧，正常20ms周期下约500ms，然后冻结。满环时触发前约2040ms、触发后500ms，合计首尾跨度2540ms。实际时间以帧时间戳为准。
4. STOP、FAULT或急停会立即结束记录；若已经触发，保留第一次原因并记录剩余后段帧数。没有欠速触发的正常动作，停车后保存尾段及停车帧。
5. 冻结后即使车辆又开始运动，也不会覆盖第一份记录。完整导出后才释放并允许下一次重新记录；复位会丢失RAM记录。

这些阈值只决定保存哪段数据，不会停车、提高PWM、重置积分或放宽保护。低于80cps、1000ms启动窗口内的短异常、不满足阈值的抖动，不保证被触发。记录第一件异常也意味着后续第二件异常可能不在窗口内；下一次受控采集应在停车导出后进行，不应连续重复多次再只读最后一份日志。

## 导出与离线解析

仍使用原有调试口`t`请求，只有runtime、控制器均非ACTIVE，且软件STBY和GPIO STBY都关闭时接受。记录过程中不打印四轮详细日志；telemetryTask在停车后逐帧导出。若导出期间开始新运动，后续导出暂停；检查后恰好进入运动时，最多可能继续打印已经取出的一帧，本版不为诊断新增运动锁。

在完整导出前不开始下一次动作。必须等到 `TRACE END; schema=2 ...`，**不能沿用旧工具固定等5秒就认定读取完成**。现有telemetryTask每帧后休眠200ms，128帧仅休眠就25.6秒，另有UART传输开销。UART打印首次失败时中止该次导出并保留整份记录，避免连续失败阻塞；重新请求应使用新的日志文件，不能把失败半段冒充完整记录。

新增 `TRACE2 BEGIN` 和 `TRACE2 SNAP`，原 `TRACE t=` / `TRACE LF/LR/RF/RR` 字段保留。旧解析工具只能看到旧字段，不会自动验证新记录完整性。

离线解析，不打开串口、不发送指令：

```powershell
python Tools/parse_motion_trace_v2.py 已保存的串口日志.txt --output trace_v2.json
```

解析器核对BEGIN/END、帧数、帧序号、四轮字段以及触发帧；缺失或重复报错。其他普通UART日志可交错存在。累计计数不作滤波、不补值、不按目标速度重建。
