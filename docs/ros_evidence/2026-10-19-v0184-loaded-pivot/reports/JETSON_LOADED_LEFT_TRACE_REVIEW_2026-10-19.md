# 地面低速左转：MCU 实际轮速目标与 PWM 采集（2026-10-19）

**本轮取得实际板上内部记录，确认低速地面轮速跟踪明显不足；方向和停车通过，转速响应仍未通过。** 不再仅依据请求角速度积分作判断，也未根据本轮自动修改固件、PI、几何或安全超时。物理阻力、电机驱动/供电和低速控制参数之间的最终根因仍需分析，不能直接判为某一个代码bug。

## 准备及操作

用户确认小车在地面、转向空间和调试线/USB/电源线余量充足、可现场停车、遥控退出。先做5秒静止检查：轮速100、激光51、IMU500样本，轮速0，/cmd_vel发布者0。使用现有底盘/EKF、雷达、原地图定位；没有Nav2或第二份底盘。

这次在静止时仅打开一次CH340（115200 8N1，DTR/RTS=false），同样发生一次PIN RESET关联事件。等待底盘恢复空闲、无故障、四轮零速及UART连续接收后，**一直保持同一描述符打开，直至动作和导出完成**。初始开口后复位计数1，ready以后没有新的MCU时间回退；没有重新校准或写Flash。串口工具仅允许停车后的一个`t`字符，不含速度/复位/校准指令。

PC桌面本地终端执行：

```bash
source /opt/ros/humble/setup.bash
unset FASTDDS_DEFAULT_PROFILES_FILE FASTRTPS_DEFAULT_PROFILES_FILE
export ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=0 RMW_IMPLEMENTATION=rmw_fastrtps_cpp
/usr/bin/python3 ~/rosdemo_rviz/pc_keyboard_teleop.py --ros-args -p linear_speed_m_s:=0.04 -p angular_speed_rad_s:=0.20
```

原安排一次j约2秒，用户实际做了两次，并确认两次左转、停车均正常，已停车且Esc退出。两次ROS动作全部保留，不改写为一次；源码在每次ACTIVE开始时清空motion_trace，因此**板上缓存对应第二次**。确认实际/cmd_vel发布者0、IDLE/NONE/四轮零速后，通过原描述符只发一次UART`t`，约31.33秒读到TRACE END，再在零速下关闭调试口。完整脚本及操作记录在证据目录，不建议脱离本次条件自动重放。

127帧、508条轮记录，源时间77461–79981ms，跨度2.520秒，最大间隔20ms；126帧ACTIVE，末帧IDLE、stop=EXPLICIT、fault=0、standby=0、PWM全0。未达到128帧上限，且首帧applied=15mrad/s，140ms后到200mrad/s，支持本次缓存覆盖第二次启动至停止，非只截取末尾稳态。该跨度与第二段ROS指令2.516秒一致到采样分辨率，不对应第一次。

目标来自实际trace，已非此前的源码推算：左右稳定±160cps。raw与filtered都低，不能仅解释为ROS滤波/解码或IMU角度问题。各轮约14.8%–50.1%的平均跟踪比例，且明显不均匀。

PI积分范围LF −48.5..−0.3、LR −31.2..−0.6、RF +0.8..+37.4、RR +1.1..+20.3‰。本段没有积分达到±50‰或PWM达到±300‰的采样；不能归因于“积分/总输出已打满”。未记录独立limited标志，不据此声称没有输出斜率限制影响。

trace的ff已包含动态breakaway项。与参考源码各轮基础FF表比较，额外量约0或±60‰；稳态段推断LF/LR/RF/RR切换14/30/15/17次。该现象与源码“速度≤20cps加启动补偿、离开阈值撤除”一致，说明低速下反复进入/离开补偿条件。**这是实际输出行为的证据，不足以单独证明补偿切换就是全部根因。** PWM最大相邻变化约20‰/20ms，需结合斜率限制及负载讨论。原始整数printf会截断浮点值，FF推断有约0.1‰级量化误差。

母线为原监测反馈，未采集高频电压波形、实际电机端电压、电流、轮胎负载/机械阻力。不能只凭当前数据区分机械卡滞、负载静摩擦、驱动供电能力与参数匹配。前后轮不同、LF/RF较低值得下位机工程师结合机械状态核对；不要求用户为此立即重复开车。
