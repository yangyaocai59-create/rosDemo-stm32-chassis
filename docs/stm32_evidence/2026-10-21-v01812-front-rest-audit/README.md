# 0.18.12 前轮恢复耗尽及低速保护复核

复核日期：2026-10-21（Asia/Singapore）。只使用已有实车数据及当前生产 C 代码；本次未连接串口、运行电机、修改生产固件、烧录或推送。当前工作区仍有此前多版累计未提交修改，不能把基线提交号当作本版发布提交。

后续更新：用户已批准恢复失败关断范围，并形成 [0.18.13 候选](../../STM32_FRONT_RECOVERY_FAILSAFE_0.18.13_20261021.md)。下面复现数据属于修改前 0.18.12 源码（哈希见 manifest）；用新版本重编译同一诊断程序时，应看到前轮持续零反馈在约 1500 ms 报告故障。原始审计记录保留，不能当作 0.18.13 当前行为。

## 已确认的软件限制

RF 目标 -160 cps、持续零反馈时，0.18.12 的运行负载上限为 45‰。确认近零速 60 ms 后启动一次恢复，临时量最多 50‰；300 ms 主动恢复结束后渐退到零。`still_ms` 仍保持确认状态，`hold_integral` 因此持续为 true，即使 `recovering=false`、`recovery=0`、`exhausted=true`，同向误差也不能使积分再增长。

对应生产代码：

- `Application/Chassis/wheel_speed_controller.c`：`WheelSpeedController_FrontSupport` 最后的 `hold_integral` 条件及 `UpdateWithMode` 的积分冻结。
- `Application/Chassis/wheel_speed_control_config.h`：RF 反向 load=45‰、I/recovery 预算=50‰、恢复=300 ms。
- `Application/Safety/fault_manager.c`：`FAULT_MANAGER_STALL_MIN_TARGET_CPS=200`，低于此目标不会进入原堵转检测。

静止输出可直接算出：

```text
基础 FF 幅值 = 56.8 + 0.14249 × 160 = 79.598 ‰
恢复耗尽后 FF = -(79.598 + 45)      = -124.598 ‰
P = 0.050 × (-160 - 0)             =   -8.000 ‰
I = 0
PWM = round(-124.598 - 8)          = -133 ‰
```

这与实车记录完全一致。输出既没有达到总限幅 300‰，也不会因同向误差继续增长；只是控制器在恢复耗尽后仍保持较低输出。原先的防积分堆积/不反复补力设计在此缺少“恢复失败后的有界结束处理”。低速保护门槛 200 cps 是已有规则，并非本版新引入；它与本版恢复状态组合后，使目标 160 cps 的长期无反馈无法升级为堵转故障。`fault=0` 只能说明未触发当前规则，不能证明电机、驱动或机械正常。

## 使用真实 C 代码复现

`front_rest_audit.c` 直接链接当前 `wheel_speed_controller.c` 与 `fault_manager.c`。反馈由诊断程序固定为零，其他任务心跳正常，周期 20 ms；没有电机动力学模型，也没有 GPIO、USB 或真实硬件。C11 / `-Wall -Wextra -Werror` 编译和执行成功。

| 轮子/目标 | 恢复耗尽后 PWM/‰ | 6000 ms 的 I/‰ | 首次堵转故障时间/ms |
| --- | ---: | ---: | ---: |
| RF / -160 cps | -133 | 0 | 无 |
| RF / -199 cps | -140 | 0 | 无 |
| RF / -200 cps | -140 | 0 | 1780 |
| RF / -280 cps | -156 | 0 | 1780 |
| LF / +160 cps | +143 | 0 | 无 |

RF/-160 的临时恢复曾升到 50‰，约 t=300 ms 的 PWM=-183‰，约 t=500 ms 后回到 -133‰，持续到 6000 ms。输出表里的“故障后 PWM”只是独立调用控制器的诊断值；实际生产 runtime 会依据锁存故障关断驱动，诊断不声称硬件在故障后继续输出。

此复现证明软件状态和保护覆盖范围，**不证明真实电机在哪个 PWM 能克服负载，也不能解释零反馈最初为何出现**。架空正常、落地零反馈仍可能与正常侧向摩擦、安装、机械、电源、驱动或编码器带载问题有关。没有实测电机端电压、电流、PWM 波形或新同步肉眼观察，不能据软件 PWM 宣称“电机已得到足够实际扭矩”。

复现命令（仓库根目录）：

```powershell
gcc -std=c11 -Wall -Wextra -Werror -ITools/tests/imu_spi_probe/stubs -IApplication/Chassis -IApplication/Safety -IApplication/Services docs/stm32_evidence/2026-10-21-v01812-front-rest-audit/front_rest_audit.c Application/Chassis/wheel_speed_controller.c Application/Safety/fault_manager.c -lm -o build/hardware_tests/v01812_front_rest_audit.exe
& .\build\hardware_tests\v01812_front_rest_audit.exe
```

`native_output.log` 为本次程序输出；`audit_manifest.json` 保存生产源文件、诊断程序及数据的 SHA256。

这些目录均为 `build/hardware_tests/loaded_pivot_compare_20261020_...`。之前把右转 720/320 ms 说成连续时长不正确；左转重复的 RF 均速应为 +253.04 而非约 +240。低速右转的 LF/LR/RR 也有离散零计数：累计分别 180/120/180 ms，最长分别 80/60/80 ms；此前表格把它们全写成 0/127 不正确。RF 在整个窗口原始计数与滤波反馈均为零，才是本轮最显著的问题。

`ground_event_audit.json` 保存所有五次逐轮连续区间、窗口截断标记及 summary；归档原始 UART/USB 和解析结果见 `ground_captures/`。此前 230423 不完整采集不纳入整段对比。第二次左转有用户观察 RF 连续；两次右转及完整低速右转没有新的同步肉眼反馈，不把“未反馈异常”写成“现场确认正常”。

## 建议的下一版范围（尚未实施）

1. 保留已验证的卸载撤补偿、原 PWM/I 上限以及立即 STOP/真实断链停车。
2. 前轮恢复失败必须有有限结束状态，不能在临时补力退出后长期冻结 I 并保持非零输出。候选行为：保留一次有界补力，超时仍无运动时锁存恢复失败并关闭所有轮输出；不得自动反复重试或扩大峰值。若评估恢复时间需调整，须先定义具体期限并离线覆盖。
3. 补齐 160 cps 等低速无反馈覆盖，而不是用 `fault=0` 放行。具体实现需选定“前轮恢复失败上报现有堵转故障”或扩展通用堵转规则；两者均改变故障触发条件，需要明确批准后落地，不能顺带全局改门槛。
4. 验证零反馈、部分欠速、运动后再次停住、真实恢复、低目标量化、换向、模式退出与计时回绕；验证失败后全轮停止、故障锁存、显式恢复及原断链/急停路径。
5. 编译候选后用户烧录；先架空检查，再做已限定时长的地面左/右对照。修复安全死角不保证某个机械负载下必然启动，仍须数据评估控制与硬件能力。

此前仅批准前轮补偿及保持安全机制。本建议新增“恢复失败关断/低速故障触发条件”，因此作为单独待确认的具体变更。现有生产源和镜像未改，不宣称已交付下一版或已解决带载问题。
