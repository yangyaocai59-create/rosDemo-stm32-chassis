# 对用户五项顿挫分析的独立核对

日期：2026-10-23。结论：**暂缓烧录现有0.18.22；软件测试通过不代表带载问题已经排除。** 本次没有修改生产源码或镜像，没有打开串口、运动、清板上故障或烧录。

## 先纠正前提

这份分析中的“恢复补力、超速P=0.15、LR反向/RR正向运行恢复”描述的是旧0.18.21执行路径，不是当前0.18.22默认转向路径。源码保留旧分支供legacy对照，不能仅凭搜到函数或旧行号就判断交付镜像正在执行它。

候选在 `WheelSpeedController_UpdateWithMode` 的统一分支提前返回；底盘转向的额外bias返回0。旧分支只在显式关闭统一宏的参考构建中执行。对应源码入口：[单轮入口](../../../Application/Chassis/wheel_speed_controller.c:884)、[底盘bias入口](../../../Application/Chassis/chassis_controller.c:114)、[新闭环](../../../Application/Chassis/unified_pivot_control.h)。

“最近6秒RR异常”没有附准确文件/源时间，不能直接当成当前最新一次事件。已有封存证据包括较长左转以及因RF保护提前结束的右转；不同固件、不同轮子、不同动作的证据应分开。下面分别核对机制与边界，不把它们合并成唯一根因。

## 五项逐条核对

| 检查项 | 对旧0.18.21的判定 | 对0.18.22候选的判定 |
| --- | --- | --- |
| 恢复触发偏晚 | 指定条件下成立；实际C代码复现160ms低于20、200ms触发 | 旧恢复脉冲不执行，但测速滤波本身未改，反馈响应仍有延迟 |
| 加/撤力不对称 | P数值成立；多项撤力具备形成循环的可能性，不是实车因果证明 | 四轮双向P均为0.05，FF固定，无旧临时补力或自适应负载撤回；物理响应仍待带载验证 |
| 左右后轮策略不同 | 旧运行恢复的所有权确为LR反向/RR正向；不能由左转推右转 | 四轮双向走同一算法，但前馈参数仍可不对称；不等于左右性能已相同 |
| 空载前馈未匹配带载/电压 | 成立；12V标定前提未核实，没有当前VM电压归一化 | 仍成立，是当前候选的重要未完成项；不能归结为电源故障 |

### 1. 滤波与触发数字的实际来源

当前配置是20ms采样、50ms滤波时间常数和200ms无计数归零。实际离散公式为：

`alpha=20/(50+20)=2/7; v[n]=v[n-1]+alpha*(raw-v[n-1])`。

若初始滤波速度240cps、之后每20ms增量都是0，则在200ms强制归零之前有 `v[n]=240×(5/7)^n`。实测C输出：140ms=22.7675、160ms=16.2625、180ms=11.6161cps；200ms因无计数超时置0。旧前轮低速确认在160/180/200ms三次各累计20ms，200ms进入恢复。本次对LF/RF、正反两个方向共四组均复现。

依据：[估计器](../../../Application/Chassis/wheel_speed_estimator.c:81)、[配置](../../../Application/Chassis/chassis_config.h:36)、`old21.log` 与 `candidate22.log` 的FILTER/SUMMARY行。

限制：这是规定输入，不是已证明的物理停轮；采样相位、真实dt、已有恢复/耗尽状态、目标大小均会改变时间。目标低于80cps时旧近静止阈值还会按目标25%降低，不能一律套20cps。200ms是这个初态的结果，不是普遍恒定的恢复延迟。旧负载恢复有“仍在移动时恢复部分负载前馈”的其他分支，也不能说所有加力都等20cps。

新候选不会等恢复脉冲触发，PI逐周期工作；但它看到的仍是同一滤波速度。实际测试中200ms的LF反转软件输出旧版约−171‰、候选约−168‰，220ms约−176/−169‰。这说明“结构简化”并不自动保证加力更大或更快，不能拿规定反馈推出实车更顺畅。

### 2. P不对称已排除，循环根因尚未证明

分别用目标±240、同向反馈140/340cps，误差幅值100，实际C得到：旧版方向归一P为+5/−15‰；候选为+5/−5‰，四轮双向均一致。旧版在恢复/负载变化时还可能冻结正误差积分，“PI仍工作”不代表旧I每周期都继续累加。

候选确实移除了这些旧执行分支，但仍有滤波、摩擦、输出限速和积分饱和。若没有带载对象响应，不能认定循环已消失，也不能仅凭旧分支存在就认定它是唯一初始原因。

### 3. 新发现：300‰不是正常闭环一定能用到的驱动力

对候选单轮代码固定目标±240cps、反馈0、I最终达到方向对应50‰上限，得到下表。这里故意只调用单轮算法计算能力边界，**没有绕过板上保护去堵转电机**；实际runtime故障保护另行测试。

| 轮子 | 正向软件PWM约值 | 反向软件PWM幅值约值 |
| --- | ---: | ---: |
| LF | 209‰ | 209‰ |
| LR | 143‰ | 148‰ |
| RF | 212‰ | 198‰ |
| RR | 159‰ | 155‰ |

原因：零反馈时P只有12‰，`输出≈FF+12+50`；全局300‰限幅并未成为限制。达到目标时P为0，可用稳态输出还会少12‰。数字为四舍五入后的软件命令，不是电机端电压/扭矩。

因此我不同意“PWM上限没打满就说明闭环有充分带载余量”，也不同意现在可以保证候选连续转动。若负载所需PWM超出这些值，即使全局上限300‰，持续PI也补不上。这是确定的算法边界，**是否真的不够仍是待测预测**。

正确后续是把I饱和、P、FF、限速状态和带载速度响应一起看，校核带载前馈和闭环调节余量。不能直接提高总PWM上限、盲目扩大I上限或重新添加按轮恢复脉冲来代替这一步。单位要分清：143‰=14.3%，不是143%。

### 4. 电压证据重新核对

历史BATTERY解码元组顺序为 `t, samples, adc_errors, raw, filtered_raw, adc_mV, supply_mV, ...`；supply是索引6，不能把samples索引1误读成电压。`run_review.py`从明确列出的两份封存decoded.json计算真实最小/最大值，结果见 `verification.json → historical_vm_mV`。这些只代表各次已记录遥测，不是今天的电压或带载瞬态示波测量。

本次核对的完整文件范围：较长左转157条遥测为10.186～10.538V，失败右转121条为10.153～10.527V，包含各自前后阶段，不能全部标为带载电压。用户给出的10.22～10.53V可能是另一份记录或子窗口，未提供原始区间，不能据此替换本次范围。

旧配置明确写着空载扫描和未核实12V；单轮FF公式不读取VM。即便某次VM低于12V，也不能直接乘 `12/VM` 作为正确补偿，因为原标定电压本身未知。你当前接法测的是降压后VM，BATTERY报文名字不代表直接测到了电池端。静态万用表正常不能排除带载瞬态，但这里没有证据把降压模块定为根因。

### 5. trace范围、同步与内存限制

实际trace录制代码经过独立测试：连续6秒、每20ms录一次并停车，保留128帧，最早3460ms、最后6000ms；时间跨度2540ms，位于2500ms的事件已覆盖。128×20=2560ms是容量量级，首末点间隔是127×20=2540ms，任务抖动还会使窗口变化。

实际链接ELF中`s_ring`大小0x4e00=19968字节，对应每帧156字节。直接保存30秒、50Hz的同样详细帧需要约234000字节，不能不顾STM32内存就把缓冲区无限放大。

还确认了一个遗漏：trace分别读runtime、controller、motor、speed和每轮PI，并不是一次完整的原子控制快照。测试在motor状态读取点注入一次模拟安全STOP，可记录到“runtime仍ACTIVE、standby已0”的混合帧。这是诊断证据的一致性限制，**不证明它导致电机顿挫**。记录PWM来自MotorDriver软件状态，驱动确实会写CCR并处理方向保护，但单条trace不证明电气输出足以克服负载。

推荐下一步诊断设计（尚未实现到生产固件）：由电机控制任务在输出提交后生成带控制序号、速度源时间、原始增量/累计计数、目标、FF/P/I、请求PWM/驱动接受PWM、CCR/standby及限幅原因的记录；处理任务级快照一致性并标记安全中断边界。在第一次合格的异常前后冻结一段预/后触发窗口，只做记录，不改变运动或保护。这样不靠无限加RAM或运行中大量文本打印，也不会继续丢掉动作中段。

## 其他要求核对

### 编码器和ROS接口

源码仍为TIM1/LF、TIM2/LR、TIM3/RF、TIM4/RR，各自差分后按配置极性累计。速度估计只读取累计值，滤波不回写累计计数；规定输入测试也确认采样没有改写上游EncoderState。USB累计计数顺序LF/LR/RF/RR，已归一轮子前进为正，名义13×4×30=1560count/rev，轮径0.065m。只需按这些约定换算，不再乘4或再次反转右轮。

这不证明带电脉冲没有漏采、接线完全正确或车体没有滑移。RR已有手转三圈的历史比例/方向证据，不必在没有新依据时重新从“轮子坏了”开始；它也不能代替所有工况的反馈验证。当前工程可审查的是固件、工具与证据，没有实际部署ROS驱动源码，不能宣称ROS端代码已审查通过。

轮子计数换算正确 ≠ 车体绝对转角正确。四轮滑移转向还受有效轮距、轮径、地面和载荷影响；需用外部朝向标记核对，不能把IMU或目标角度写回计数来达标。

### 安全门槛并非“已经全低速覆盖”

原200cps门槛仍在，但说候选“后轮低速全无保护”不对：候选≥20cps的连续近静止1500ms已覆盖四轮。实际runtime/controller/fault-manager在20.05和160.43cps目标、0反馈时，所有轮/双向均约1500ms锁存停车。

覆盖仍不完整：160.43cps目标、21cps反馈略高于近静止阈值20，却低于目标15%；由于目标不足200，该输入6秒内不触发这两类堵转路径。240.64cps目标、30cps反馈则在约1760ms由严重欠速路径停车，四轮双向一致。以上均是规定输入的软件边界，不等于实际机械堵转。

没有为减少停车而关闭保护或继续放宽门限。本次重新跑过统一闭环/停车回归、USB20组、协议自测和里程计数学自测；这不表示功率、电流、机械故障或所有低速故障都已覆盖。

另外实际runtime新增验证：只提交一次速度命令，不再发第二包，四轮仍在每个控制周期持续工作至240ms；到250ms命令过期才按原机制立即停机。持续有效目标不需要每包“点动一下”，但上位机仍须在超时前刷新命令，状态查询不是运动命令续期。

## 独立判断及下一步

事实：旧机制中确有上述延迟和不对称；候选已避开旧补偿路径；候选前馈仍未完成带载标定；记录短且不是完整同步快照；候选存在明确的输出调节余量与低速保护适用边界。

预测：统一PI可能减少阶段切换，但也可能因旧前馈/I上限使某轮驱动力不足；不能从单测判断最终顺畅程度。历史计数平台可能对应近停、反馈遗漏、净增量抵消或观察分辨率限制，当前不能唯一归因于轮子或软件。

判断：**暂不建议按上一轮交付提示立即烧录.22去长转向。** 先把异常捕获和同步诊断方案补齐，再决定对同一控制算法的FF/PI标定；不是回到每个轮子单独叠加补偿。真正带载响应和角度误差不可能完全靠离线证明；之后必须分“诊断候选小范围受控验证”与“性能验收”两步，不能承诺烧录前已经排除所有实车问题。

本轮没有改生产参数、保护、trace或固件版本。172项受审查生产/测试文件及.22四个产物哈希在检查前后保持一致，旧候选未覆盖；只新增本目录的审查程序、原始测试输出与结论。

运行入口：`python docs/stm32_evidence/2026-10-23-v01822-user-review/run_review.py`。C测试分别链接冻结.21与当前.22的真实单轮控制器，使用真实估计器/trace/runtime代码，外围输入为模拟。没有物理电机模型，没有硬件性能通过声明。
