# 0.18.21：RR 计数平台触发停车取证

2026-10-22，Asia/Singapore。只执行了已批准的一次落地左转：0.30 rad/s，最长6秒。实际约3.266秒时主机发现RR累计计数平台，发送正常STOP保留异常前环形记录；不是固件堵转故障，也不是人为断电。没有清故障、重试或重新烧录，最终四轮静止、端口关闭。

## 结论先行

**RR反馈间歇已经在STM32内部、USB发送之前出现；不能只归咎于ROS解码。但目前还不能区分实际轮子短暂停滞与带电条件下的编码器反馈异常，也不能宣布里程计验收通过。**

用户回看录像报告：“RR一直转动，直到整车自动停车”。这是重要的现场证词，但尚未收到录像原片，不能写成独立逐帧验证。若原片确实显示在同一120ms窗口内RR持续、单向、可分辨地转动，那么应优先排查编码器A/B信号、供电、接插件及MCU输入采集链，而不是继续加PWM。若原片显示同窗近停，则继续分析负载和控制恢复；PWM非零不等于实际转速非零。

本轮不修改固件、编码器倍率、ROS轮距、IMU或安全策略，不制作0.18.22，不追加运动。

- 六个连续20ms估计区间的RR净增量均为零，覆盖120ms；第一和最后记录的时间戳相差100ms。不能把它直接称为120ms物理堵转。
- USB同期RR累计计数保持2577，主机在达到100ms平台门限后停车。六帧中目标240 cps、ACTIVE、standby=1、fault=0不变，基础/合并前馈96.8‰不变，I和软件报告PWM逐渐增大，没有在该窗口内被软件突然切为零。
- **异常之前确有撤力过程**：RR滤波由237升至326 cps，输出从118降至95‰，随后增量下降。这既可能是控制/负载振荡的一部分，也可能是反馈变化所致；仅凭时序不能确定唯一因果，更不能排除前馈退场设计的问题。
- 同窗LR/RF每个20ms区间仍有非零增量；LF末尾两帧为零，且此前存在更长的欠速段。不能只看RR就认定四轮跟踪合格。
- UART记录1735636收到正常STOP，下一条trace源时间1735643为IDLE/EXPLICIT、standby=0、四轮PWM=0。停车后RR一帧dc=1，稍后累计2574，可能存在微动/回弹或反馈方向变化，不能凭此单独断言机械回弹或计数损坏。

## 一致性和证据边界

- 收到128帧完整四轮trace，127帧ACTIVE，20ms连续，无时间缺口；65条速度命令均接受，accepted从120升到185，rejected=0。固件故障0/0，最终STATUS IDLE/EXPLICIT、flags=0x0150、请求和四轮速度为零。
- 采集报告CRC、RX overflow、TX drop为0，motor/safety周期20/10ms，overrun=0/0。离线重新按`<Iqqqqiiii`解包全部保存的0x82 payload，与采集时记录逐项一致。JSON仅保存payload，没有完整含CRC线帧，不能宣称独立重验了线帧CRC。
- 运动阶段USB供电遥测10.241～10.527V；低频遥测不能排除瞬时压降、地弹或编码器供电干扰。
- UART `1735532 ENC R`：RR raw=62959、d=1、total=2577；SPD打印RR dc=0/cps=93。ENC与SPD/trace是不同来源快照，且日志行前缀是打印时间，不是共同采样时间。**并没有连续100ms的TIM4寄存器直读或A/B边沿波形，不能声称本次直接证明硬件CNT始终冻结。**
- 对四路累计值的快照与USB打包做源码复核，未找到本次现象对应的轮号/有符号64位打包错误。trace跨runtime/controller/motor/estimator分次取快照，边界并非全事务原子，不能把单帧所有字段解释为同一硬件瞬间；持续六帧的反馈平台又不能仅用单次快照边界错位解释。

## 引脚和采集代码复核

- RR=TIM4，PD12/PD13，AF2，TI12、ARR65535、prescaler=0、IC1/2 filter=6。方向归一化−1。PWM使用TIM8 CH4，不是TIM4。
- 方向输出PD6/7；公共STBY PD10（PD11保留低）。急停是**PC13**，不是PD13。安全GPIO清零掩码不包含PD12/13。MPU6500 SPI和保留I2C1 PB6/PB7不占用RR脚。
- 在已搜索的Application/Core运行调用路径中，Encoder Start位于一次初始化；Stop只用于初始化失败回滚。没有找到运行过程中重启/停止TIM4或清零CNT的调用。生成的DeInit函数存在，但未找到业务调用。
- `system_stm32f4xx.c`中整端口GPIOD改写属于条件编译的外部内存初始化；当前构建命令没有启用`DATA_IN_ExtSRAM/ExtSDRAM`，源码中的定义也被注释，不构成本次运行中覆盖证据。
- motorTask顺序：EncoderService_Update → WheelSpeedEstimator_Update → ChassisRuntime_Process → MotionTrace_Record。定时器读取四路后，原始值/增量/64位累计值在临界区发布；估计器由累计差算raw再滤波；USB从同一轮速快照携带累计值和滤波cps。滤波不会直接清掉累计计数。
- 这只是源码路径审查，不是硬件寄存器读回验证。没有证据支持现在随意改filter、上拉、倍率或扩大堵转阈值。
