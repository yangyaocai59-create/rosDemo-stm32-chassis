# 0.18.13 前轮欠速：移动期撤载与积分抵消复核

2026-10-21，Asia/Singapore。范围：已有记录及真实控制 C 代码的离线诊断。本轮未接触串口、未发运动/清故障命令、未改生产固件、未编译 ARM 镜像或烧录。

## 结论

已确认一个固件侧改进点：**前轮短时超速会立即快速撤减负载补偿，而移动欠速时，负载重建只从已有正向积分搬运，搬运本身不增加 FF+I 总量。记录中两种作用几乎互相抵消，导致 RF 虽然平均明显欠速，净支撑却基本不增加。** 这不是积分已到 50‰ 上限，也不能因为 I 约为 10‰ 就误判 I 没有工作；它确实持续产生误差修正，其中一部分被重新分类进负载项，另一部分又随超速撤载消失。

这能解释该段持续欠速为何没有较快纠正，不能单独解释最初的速度波动、上一轮为何持续停住，亦不能排除地面负载、驱动或反馈因素。0.18.13 的自然恢复失败关断证据仍成立，不削弱或取消该保护。

## 同一段 RF 数据的逐步平衡

数据来自[上一轮重复右转](../2026-10-21-v01813-ground-failsafe/repeat_134912/README.md)，仅分析末段 127 条 ACTIVE trace（1845602..1848122，dt=20 ms）。两端差分对应 126 个更新间隔。

- 显示目标 -160 cps；按当前几何计算的实际目标约 -160.428 cps。
- 平均显示反馈约 -115.055 cps，RF 在该窗口没有绝对值≤20 cps 的近零反馈。
- 7 个采样满足“同向速度大于目标约 20 cps”的撤载条件，旧规则每次最多撤 200‰/s ×20 ms=4‰，合计名义撤载 28‰。
- 根据同一段误差及 Ki=0.25 计算，普通误差积分净增加约 28.020‰，与撤载几乎相等。
- 实际记录的同向 `FF+I` 从 114.7‰ 到 114.8‰，仅增加约 0.1‰。源码平衡预测约 +0.020‰，逐步最大差异约 0.097‰，在打印截断精度范围内。

因此，这不是仅从两个均值猜测：每一步的变化都与“正常积分—快速撤载”平衡吻合。P 项仍在单独响应瞬时误差，此处的 FF+I 并非完整 PWM；RF 实际 PWM 均值约 -115.13‰。

计算方法：第一帧滤波状态只知整数截断区间，选其中点；之后使用已记录 raw 和 20/(50+20) 的滤波递推。全部 127 个 reconstructed filtered 值截断后与记录一致。初值仍有不足 0.5 cps 的不确定性，不能说获得了 MCU 全精度内部状态。trace 也没有独立输出 load/recovery/hold 状态，因此名义撤载及积分归因仍是源码与记录共同支持的推断，而非新增私有状态读数。`support_balance.json` 保存时间点、数值、误差和哈希。

## 真实 C 代码的独立核对

`support_probe.c` 链接真实 `wheel_speed_controller.c`，不给 GPIO/串口/电机模型。LF/RF、正反方向共 4 组均通过：

1. 目标 160 cps，已稳定输出，正向 I=10‰。
2. 规定一次 20 ms、200 cps 的超速反馈：FF+I 减少 4.2‰（撤载 4‰及普通积分 -0.2‰）。
3. 随后规定持续 115 cps 欠速：FF+I 每步只增加 0.225‰，约需 380 ms 才补回这一单次 20 ms 超速造成的下降。
4. 此过程中无近零、无恢复失败、未到 PWM/I 限幅。

这是策略响应的确定性演示，**不是物理电机闭环模型**，不能据此声称实车在修改后一定稳定或一定跟上目标。

另外重跑现有 `Tools/tests/run_motion_tests.ps1`，29 条 PASS，含 1500 ms 恢复失败关断、显式清故障及 STOP/断链/超时/急停等安全路径。测试通过表明实现符合当前测试，不能取代带载性能验收。130 个生产/配置/测试文件与交付 0.18.13 的 source_manifest 哈希仍完全一致。

## LF 的区别

LF 同一窗口平均 +97.73 cps，目标约 +160.428；有 19 条离散近零反馈（总计 380 ms，最长连续计账 160 ms），以及临时补力活动。LF FF 峰值 181.5‰，高于基础前馈约 75.223‰+负载上限 60‰，说明存在额外临时补力，不能把全部 FF 都当作长期负载项。用户这轮只观察 RF，没有对 LF 做独立物理连续性确认。

LF 还叠加了临时恢复/退出及积分冻结，不能把 RF 的简洁移动期平衡等式机械地套成 LF 的完整根因。两前轮均欠速，后续验证需要同时看四轮，不再只凭 RF 一轮外观判断控制已经通过。

## 建议下一版的最小范围（尚未实施）

本节保留诊断时的待批准方案。后续用户已批准并完成[0.18.14 候选实现/离线验证](../../STM32_FRONT_LOAD_CONFIRM_0.18.14_20261021.md)，尚未烧录/实测；以下“尚未实施”描述对应本次历史诊断阶段，不覆盖新的版本状态。

首选只调整**前轮移动期负载撤减的时间确认**，而不是同时加大 PI、抬高车速、增加补力或改编码器滤波：

- 短时超速继续立即使用现有 P 阻尼和正常 I 回退；快速撤减长期负载项先要求连续超速确认。可先以 60 ms 累计阈值做候选验证，而非最终定值。
- 持续超速确认后，仍按现有速率撤载到零；不取消架空卸载时减力的能力。临时 recovery 遇到超速仍应立即结束，不能等这个新确认计时。
- 欠速时保留原 PI、搬运预算及全部上限；先评估仅消除短时重复撤力能否改善净纠偏，不同时引入第二套欠速增力。
- 保留 1500 ms 恢复失败、原有 PWM/I/补力峰值、斜率、STOP/断链/超时/急停/故障锁存，直行、后轮、USB、编码器、IMU 不变。

冻结这段原始反馈做判据回放时，60 ms 候选只在 1847182/1847202 两个时刻满足（旧规则有 7 个时刻）。这仅说明判据差异；更改后真实反馈会改变，不能把这 7→2 当成新固件实车性能结果，也不能直接预测能多转多少或一定消除顿挫。20 ms 采样下 60 ms 计账含首个更新步，三条记录首尾时间差为 40 ms，不把它包装为独立硬件精确延迟。

若用户批准实施：先补离线短脉冲/持续超速/欠速/模式与符号切换/实际 dt/失败关断边界测试，再做完整回归及 ARM 编译；用户烧录后先架空确认卸载超速仍受控，再落地左右对照。此阶段尚未实施或发布 0.18.14，也没有要求用户现在移动或重新烧录。
